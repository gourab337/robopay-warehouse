The problem it solves
Warehouses increasingly run mixed robot fleets from different vendors: picker robots, carrier AMRs, and charging docks run by separate operators. Each vendor fleet is a walled garden. There is no neutral way for one vendor's robot to hire another vendor's robot, or to pay a dock operator for charge, without a central platform acting as middleman and ledger. RoboPay Warehouse gives every robot its own wallet and a shared on-chain job market. Robots can take work, subcontract work to robots from other fleets, and pay for the services they use. Payment is escrowed and only released when the receiving party confirms the handoff, so fleets that do not trust each other can still cooperate.
What it does
1. The warehouse posts an order (e.g. "pick SKU-42") with 10 mUSDC locked in escrow. 2. A picker robot (fleet A) accepts the order and drives to the shelf. 3. The picker uses its own wallet to post a sub-job paying 3 mUSDC, hiring a carrier robot (fleet B) to move the tote to packing. 4. The picker commits to the tote on-chain as a hash, without revealing it. The carrier delivers to packing, generates a zero-knowledge proof of delivery (about 1.6 s on a laptop CPU) and submits it. HSK verifies the proof on-chain and pays the carrier automatically. Nobody has to confirm. 5. The picker submits the order. The warehouse confirms and the picker is paid 10 mUSDC (7 mUSDC margin). 6. When a robot's battery runs low it drives to the charging dock and pays the dock operator per unit of charge (0.1 mUSDC/unit). 7. Every completed job increments the worker's on-chain reputation counter. Everything runs live on HSK Chain testnet. The dashboard shows each robot's status, battery, balance and reputation, plus a live transaction log linked to the HSK explorer.
What's novel on-chain
This is more than a token transfer: - Nested escrow: a robot is both a worker (for the warehouse) and an employer (of another robot). Each sub-job stores a parentId linking it to the order it serves, so the chain holds a full trail of which robot did what for whom. - Pay on receipt: funds are released only when the next party in the chain confirms the handoff, so robots from different vendors don't need to trust each other or a platform. - HashKey KYC SBT: only KYC-verified operators can post top-level orders; a robot can only subcontract work it has accepted. - On-chain reputation: JobMarket counts completed jobs per robot wallet (completed[worker]), giving a public track record other robots can use when hiring. - Machine-to-machine payments: robots pay the ChargingDock contract directly for energy, with no human in the loop.
How we built it
Smart contracts (Solidity, Foundry, OpenZeppelin), deployed on HSK Chain testnet: - MockUSDC: 6-decimal testnet stablecoin. - JobMarket: escrowed jobs with post / accept / submit / confirm / cancel, parentId for sub-jobs, a completed-jobs reputation counter, and setToteCommitment + submitWithProof for ZK-gated payment. - HonkVerifier: generated by Barretenberg from our Noir proof-of-delivery circuit. Custom errors fail fast on wrong status, wrong caller or zero reward. - ChargingDock: charge(units) transfers units × price from the robot to the dock operator. - 7 Foundry tests (including a real ZK proof verified in the EVM and a tampered proof rejected) cover the full robot-subcontracts-robot flow, accept races, access control, refunds and dock payments. Frontend and agents (Vite, React, TypeScript, viem): - 2D warehouse simulation (shelves, packing station, charging dock) on a canvas. - Each robot is an autonomous agent loop with its own wallet. It scans open jobs, accepts them, moves, subcontracts, confirms and recharges on its own. - Every transaction is simulated before sending, so a robot that loses a race for a job backs off without wasting gas; reverted receipts are treated as failures. - Contract addresses and ABIs are read straight from the Foundry build and deploy output, so the app and chain never drift apart. No hardware is needed for the demo. The agent logic has no UI dependency, so the same loop can drive a real robot through a ROS bridge.
Challenges we ran into
Two robots could accept the same job in the same block. The losing transaction reverted on-chain but looked successful to the client. We fixed it by simulating every call first, treating reverted receipts as errors, and spreading robots randomly across open jobs. HSK's load-balanced RPC sometimes returned a stale nonce right after a transaction was mined, so robots' next transactions were rejected with "nonce too low". Each robot now tracks its own nonce locally.

Privacy & ZK

Privacy & ZK (built and live on HSK)
Zero-knowledge proof of delivery, live on HSK Chain testnet: - When the picker hires a carrier, it commits to the tote on-chain as pedersen(tote_id, job_id). The tote ID itself never goes on-chain. - The packing station reveals a scan secret to the robot that delivers the tote. The carrier generates a Noir proof (UltraHonk, about 1.6 s on a laptop CPU, no GPU) that it knows both the station secret and the committed tote. - The proof is bound to the job ID and to the carrier's own wallet address, so it can't be replayed for another job or by another robot. - JobMarket.submitWithProof calls a Barretenberg-generated HonkVerifier contract on HSK. If the proof is valid, escrow pays the carrier immediately. Payment is released by math, not by the other vendor's word. - Robots are pseudonymous wallets; raw sensor data stays on the device. Honest limits of the prototype: the station secret is a demo constant (in production it lives in the scanner's secure element and rotates per scan), and tote commitments need a random salt so they can't be brute-forced.

Demo script · 3 minutes

  1. 0:00 Problem in one line: robots from different vendors can't hire or pay each other without a middleman.
  2. 0:20 Click Start robots. Each robot approves the market and dock from its own wallet; the tx log fills with HSK explorer links.
  3. 0:40 Click Post order. The warehouse locks 10 mUSDC.
  4. 1:00 A picker accepts, drives to the shelf, then posts a 3 mUSDC sub-job. A carrier from the other fleet accepts it.
  5. 1:40 The carrier reaches PACK, its status shows "generating ZK proof", then submitWithProof lands on HSK and the carrier's balance goes up with no one confirming. The warehouse confirms and the picker is paid.
  6. 2:10 A robot's battery goes red, it drives to the dock and pays for charge on-chain.
  7. 2:30 Point at the "jobs done" column: on-chain reputation. Open one tx on the explorer to prove it's live.
  8. 2:45 Close with the roadmap: the same agent loop drives a real robot via ROS.

Roadmap

Real robot via ROS bridge

Run the same agent loop on a physical AMR or arm.

Robot identity

A DID or ERC-8004-style agent registry so each robot has a verifiable on-chain identity.

Reputation-weighted hiring

Robots choose subcontractors by completed-job history.

LLM planner

An agent that negotiates sub-job prices instead of using fixed rewards.

Real stablecoin on HSK mainnet

Replace MockUSDC with a live stablecoin.

Hardened ZK

Secure-element station secrets that rotate per scan, salted commitments, and posting plus committing in one call.

Dispute window

A timeout and challenge period before escrow releases.
